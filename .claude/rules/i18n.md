# i18n Conventions

- Messages are split per namespace: one file per feature/page in `apps/<app>/messages/{en,uk}/<namespace-file>.json` (e.g. `navigation.json`, `home-page.json`) — never a single `en.json`/`uk.json` per locale. Reference: `example/track-my-life/apps/money-tracker/messages/`.
- Namespaces are registered once in `packages/shared/src/constants/i18n-namespace.ts` (`I18N_NAMESPACE` as-const + `I18Namespace` union) and mapped to file names per app in `src/i18n/constants/localization-messages-file-name-by-namespace.ts`; `getMessagesByLocale` (`src/i18n/utils/`) loads and deep-merges them with EN fallback.
- Every key lands in BOTH locales in the same commit — `pnpm i18n:parity` gates missing/extra keys and files (EN is the reference locale).
- Keys: nested camelCase, ICU interpolation only — no string concatenation for sentences.
- Component usage: `const translate = useTranslations(I18N_NAMESPACE.<ns>)` (the repo-wide `id-length` lint rule rejects `t`). NEVER hardcode the namespace string literal — reference the namespace constant. There is ONE shared constant for the whole monorepo: `I18N_NAMESPACE` in `@supertool/shared` (`packages/shared/src/constants/i18n-namespace.ts`), imported by both apps and the framework-pure packages (`packages/ui`, `packages/shell`, `packages/widgets`) — `shared` sits below them in the dependency graph, so this is not an app constant and adding a namespace means adding one entry there.
- The namespace constant holds only top-level (file) namespaces — one entry per message file, NOT per nested key. Compose nested sub-namespaces with a template literal at the call site: `useTranslations(\`${I18N_NAMESPACE.navigation}.localeSwitcher\`)`.
- Real Ukrainian translations, not transliterated English.
