## What Went Well

- **The single carried-over Epic 6 action item — the flaky Testcontainers teardown race — was fixed in 7-1 and held green through the rest of the epic. Clean 1-for-1 close-out, and the last standing CI annoyance is retired.** Epic 6 retro Action #1 named 7-2/7-3 as candidates for the pool-drain fix "at the first Epic 7 backend touch," but the dev correctly recognized that **7-1 is the actual first backend touch** (it adds a migration + users-module changes + integration coverage) and folded the fix there (D-F). The `stopIntegrationApp({ app, container, poolList })` helper was added to `integration-app.ts` and adopted by **all 11** integration `afterAll`s at once (signature widened from the story's literal `{ app, container }` to also drain heterogeneous per-spec pools). Every subsequent backend story (7-3, 7-5) booted through it and reported **no `57P01`/`ProcessInterrupts` teardown error, deterministically — not "green on retry."** The three-consecutive-epic pattern of assigning each deferred item a *named owning story* continues to pay off: the re-run tax that Epic 6 flagged as "unpaid debt that compounds per backend story" is now paid off permanently.
- **The better-auth-native pattern matured into a clean, articulated decision rule — authClient vs custom endpoint chosen deliberately per operation, and recorded each time.** Three account operations, three different mechanisms, each with a stated *why*: **7-1** persists first/last through better-auth **additional fields** (`input:true`) in the same sign-up call (mirroring the existing `role` field) and keeps the core `notNull` `name` as a derived display value — because better-auth owns the identity row and sign-up must go through it. **7-2** uses the native **`authClient.changePassword`** with **no endpoint at all** — because better-auth already owns credential verification/hashing/session handling; adding a NestJS endpoint would duplicate it and bypass the host (zero drift was the consequence, not the goal). **7-3** deliberately does **not** use better-auth's `deleteUser` plugin and instead adds a **custom `DELETE /users/me`** — because the dangerous multi-table transactional cascade must live in a properly-injected, unit- and integration-tested repository (D7), and better-auth's `beforeDelete` hook runs at module-load time outside Nest DI where it cannot cleanly own or test that purge. The implicit rule the epic settled: **use the native authClient path when better-auth already does the operation well and no DB-touching domain logic is required; add a custom endpoint when the operation needs a tested, injected repository transaction over domain tables.** Every one of these was flagged as a `D-x` for operator confirmation.
- **Every security-sensitive surface this epic added was verified with a dedicated integration test *and*, where behavior only shows at runtime, a live running-app check.** Four genuinely sensitive surfaces landed and each carries proof: **change-password** (7-2 — integration asserts new password signs in, old password fails, wrong current password rejected, unauthenticated rejected, and the session survives without `revokeOtherSessions`); **account deletion** (7-3 — integration seeds user A with a *two-level category hierarchy AND transactions referencing those categories* so the `RESTRICT`-FK ordering is genuinely exercised — a naive `DELETE FROM users` would fail on that data — then asserts A's five row-classes all = 0, B's all intact, A's stale cookie → 401, unauth → 401); **public-route gating** (7-4 — live-verified signed-out `/` and `/uk` render the landing, signed-in redirects to `/dashboard` in a single hop with no loop, per memory `verify-middleware-redirect-changes-live`); **helmet/CSP** (7-5 — integration asserts headers present and `Content-Security-Policy` absent, plus a live running-stack check that Swagger renders, the same-origin proxy + cookie forwarding + auth + gzip all work end-to-end). The Epic 6 D4 standard ("every destructive/injection/cross-user surface ships a dedicated integration test proving the safety property") held, and 7-4/7-5 extended it with the running-app check for behaviors gates cannot catch.
- **The autonomous adversarial review loop caught a genuine must-fix on 7-4 and the fix→re-review cycle closed it cleanly — the one CHANGES-REQUESTED of the epic.** 7-4's three-layer review returned CHANGES-REQUESTED on one real blocking defect: `AdvantagesSection` rendered `<CardTitle variant="title-s">` → `<h4>` directly under the section `<h2>`, **skipping `<h3>`** and violating AC6's "correct heading hierarchy" on the app's first public, SEO-relevant page. ## Challenges & Recurring Patterns

1. **7-5's story text carried two factual errors about middleware defaults that only surfaced at red/green — caught by the dev, but a reminder that "assert the documented default" beats "assert the guessed default."** The story prose (AC-1 / Task 4) asserted `X-Frame-Options: DENY` and listed `x-no-compression` as a suppression path. Introspecting the actually-installed middleware showed helmet 8.2.0's frameguard default is **`SAMEORIGIN`** (D-8) and that `compression` 1.8.1's bundled default filter **does not honor `x-no-compression`** (that opt-out only exists with a custom filter, which D-3 forbids) (D-9). The dev corrected both against the installed behavior rather than forcing an override (which would have violated D-2 "keep all non-CSP helmet defaults") and recorded them as new D-x. No harm done, but the story was written from library-docs/reference memory rather than the pinned version's real defaults — a small instance of the recurring "verify framework behavior against the actual installed version" lesson (memory `feedback-verify-before-apply`). Lesson: for a middleware/library-defaults story, assert the *observed* default of the pinned version, and treat any specific header value in the story prose as a hypothesis to confirm.
2. **The name single-writer rule (7-1) produced a non-obvious ripple — the user-menu locale switch could no longer send `name` — resolved correctly with a new focused action, but it was a design consequence the story didn't fully pre-map.** Making `name` derived-only (removed from `UpdateUserDto`, composed from first/last) meant the existing `AppShellSection.handleLocaleChange` call of `updateProfile({ name, locale })` became impossible (the form schema now requires `firstName`, and re-deriving parts from the composed display name would corrupt stored values). The dev added a focused `update-locale` server action (mirroring the established `update-default-currency` pattern) — the right call, and it preserves the single-writer contract. But it re-touched the exact `AppShellSection` locale-switch coupling that a 1-6 deferral had already flagged (`shell locale switch always sends name`), and closed it as a side effect. Lesson: a "single-writer / derived-field" refactor has a blast radius equal to *every* existing writer of that field — enumerate them at design time (the 1-6 deferred item was the early warning).
3. **7-3 introduced a real, deliberate purge but left one transient table (`verifications`) intentionally untouched — correct today, but it is the one place "delete all my data" is not literally complete.** The cascade purges transactions, categories, sessions, accounts, and the user row, and invalidates the analytics cache — but `verifications` (better-auth's `identifier`-based transient tokens, no user FK) is skipped by design because it has no user linkage. For the current PoC (no email-verification/password-reset flows are enabled) the table is empty or holds only short-lived tokens, so this is genuinely fine. But it is a latent gap the moment better-auth's verification flows are turned on: a deleted user's pending tokens would linger until TTL expiry. Worth a note in the delete path so a future "enable email verification" story remembers to purge them by `identifier`.
4. **7-4's footer cannot expose a `contentinfo` landmark, an inherent consequence of the (correct) no-route-group decision — accepted as a PoC limitation but it is a genuine a11y gap on the public page.** Per ARIA-in-HTML, a `<footer>` nested inside the shell's single `<main>` maps to a generic element, not `contentinfo`. This falls straight out of the pre-approved D-1 (no route group; `AppShell` owns the one `<main>`) plus the deliberate double-`<main>` avoidance. The review raised it as an operator-judgment decision item; it was accepted rather than force-fixed with a `role="contentinfo"` (which has its own nesting caveat). It is the clearest small tension between the no-route-group shell decision and full landmark semantics on a marketing page, and belongs in the standing tech-debt list if the public chrome is ever revisited.
5. **7-4's committed visual-QA evidence was a *subset* of the enumerated AC-8 matrix — the full-page 4-way matrix does cover every section, but the story's own AC listed more standalone captures than were committed.** The committed set (full-page all-4, faq-expanded all-4, hero-desktop-light, full-page-uk-desktop-light — 10 files) omits standalone `advantages`/`reviews`/`faq-closed`/`footer` captures and only shows hero + uk at desktop-light. The reviewer judged that the full-page 4-way matrix shows every section in both themes/viewports and `faq-expanded` covers the interactive state, so core evidence exists — and flagged it as an operator's-call item rather than a must-fix. This echoes Epic 6's Challenge #1 (a UI story's evidence matrix drifting from what the ACs enumerate); the committed-evidence gate is only as strong as the match between the AC list and what actually lands. Lesson: when an AC enumerates a specific capture list, the dev should either produce it or amend the AC in the record — a full-page matrix is good coverage but not literally the enumerated set.
6. **The charter's hedges ("(optional) reviews", "session behaviour follows better-auth's default", "cascade the user's data") were all resolved decisively in dev, in the exceed-the-reference direction — continuing the Epic 5/6 pattern.** 7-4 kept the optional reviews section (parity + it reads as a real marketing page); 7-2 bound to better-auth's session-preserving default *and* added a confirm-password field the reference lacks (and flagged `revokeOtherSessions:true` as the stricter road not taken); 7-3 chose a hard ordered cascade over the reference's soft-delete and type-to-confirm over password-re-entry, both flagged. Every resolution was recorded as a `D-x`. This reaffirms Epic 6 D5: charter implementation notes are hypotheses to resolve in dev with a recorded rationale, not constraints — and the unattended run kept flagging them as operator-confirm points even though confirmation resolved to merge-time acceptance.

## Key Insights

1. **A per-operation "authClient vs custom endpoint" decision rule is now the platform's settled way to build on a managed auth host.** The three account operations crystallized it: native authClient when the auth host already does the job and there's no DB-touching domain logic to test (7-2 change-password), a custom tested endpoint when the operation needs an injected repository transaction over *domain* tables (7-3 delete-cascade), and additional-fields-through-the-host when persisting extra identity data at sign-up (7-1 names). The load-bearing tie-breaker is **testability under D7**: better-auth's out-of-DI, module-load hooks can't own a tested cascade, so the dangerous path gets a real endpoint even though the "zero-drift" path was available. This rule is worth stating explicitly for any future auth-adjacent feature.
2. **"Derived field with a single writer" is a powerful invariant but its blast radius is every existing writer — enumerate them before the refactor.** 7-1's `name`-is-derived rule was correct and kept display/parts from ever diverging (even on a partial PATCH, via service read-merge-compose), but it broke the user-menu locale switch (an existing `name` writer) and forced a new `update-locale` action. The early-warning was a *1-6 deferral* that had already flagged "shell locale switch always sends name." Lesson: when introducing a derived/single-writer field, grep every writer of the old field first — the deferred-work ledger often already lists them.
3. **For a library-defaults story, assert the observed default of the pinned version, not the documented/remembered one.** 7-5 shipped correct middleware but the story prose guessed two defaults wrong (`X-Frame-Options: DENY`, `x-no-compression` honored) that the pinned helmet 8.2.0 / compression 1.8.1 don't match. The dev caught both at red/green and asserted reality. A story that pins exact versions should introspect those versions' actual behavior for its assertions — the reference's older pins and the package README are hypotheses.
4. **The committed-evidence visual-QA gate is only as strong as the match between the AC's enumerated captures and what lands — a full-page matrix is good coverage, not literal compliance.** 7-4 committed a full-page 4-way matrix (covering every section) plus the interactive faq-expanded state, but omitted several standalone captures the AC enumerated. Core evidence existed and the review accepted it, but the drift between "AC says capture X, Y, Z" and "committed A, B" recurs (Epic 6 Challenge #1). Either produce the enumerated set or amend the AC in the record so the gate stays honest.
5. **"Delete all my data" is a claim that must be audited against the full schema, not just the obviously-user-owned tables.** 7-3's cascade is complete for every table with a user FK, and it correctly reasons that `verifications` (no user FK, transient) is out of scope today. That reasoning is sound *now* but silently becomes incomplete the moment email-verification/password-reset flows are enabled. A destructive "purge everything" operation should carry an explicit inventory of *what it does not touch and why*, so a future feature that adds user-linked transient data remembers to extend it.

## 🚦 Decisions Logged This Retro

_All synthesized from the evidence trail (non-interactive run) — each traces to a decision already recorded in a story file or review thread; none are new policy invented here._

- **D1 — Per-operation auth mechanism selection is the standing pattern on better-auth** (native `authClient` when the host owns it with no DB-touching domain logic → 7-2; additional-fields-through-the-host for extra identity data at sign-up → 7-1; a custom tested endpoint when the operation needs an injected repository transaction over domain tables → 7-3). The tie-breaker is D7 testability. Record the mechanism + rationale as a `D-x` every time.
- **D2 — Know and verify the generated-client drift *class* on every contract-touching story** (additive-only / real-regenerate / no-op), each confirmed with `git status --porcelain packages/shared/src/generated` (precedents: 7-1 additive, 7-3 real-regen, 7-2/7-4/7-5 no-op). Generalizes Epic 6 D1 from "additive-only" to "the right drift class, explicitly verified."
- **D3 — Every security-sensitive surface ships a dedicated integration test proving the safety property, *and* a live running-app check where the behavior only shows at runtime** (precedents: 7-2 change-password flow, 7-3 cascade/scoping/session-termination, 7-4 public-gating redirect, 7-5 helmet-headers + proxy/Swagger/gzip).
