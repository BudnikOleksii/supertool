# Story 5.2: Standalone Import Page

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Oleksii,
I want a first-class page to upload a file, preview what will import, and execute,
so that I can bring my own data in confidently — exceeding the reference's bare file input (RP-F2).

## Context & Why This Story

Story 5-1 shipped the contract (merged PR #34): `POST /api/v1/transactions/import` + `/import/preview` on the transactions controller, exposed through the generated client as `TransactionsApiService.transactionsImport` / `transactionsImportPreview` (multipart body `{ file: Blob | File }`). Nothing renders it yet — the sidebar "Import" entry is a `disabled: true` placeholder (epic-4 retro action #3 assigns the flip to this story), and the only user-visible import remains the boot seed. This story builds the standalone import page at `/transactions/import` (route constant already exists): a styled drag-drop upload → server-computed preview → confirmed execute → on-page result, fully mobile-usable, closing the user-facing half of RP-F2 (P0).

The parity bar is **exceed, don't replicate**: the reference's standalone import page is a bare native `<input type="file">` with no drag-drop and no styling (spike §5 defect; capture `import--page`), and its "preview" is a client-side papaparse+zod pass that knows nothing about duplicates or existing categories. Supertool's server preview is strictly richer — dedup counts (`newRows`/`duplicateRows`), categories that would be created, near-duplicate warnings, collect-all row errors — so the page is built on it (see decision D-A). After a successful import, Story 4.3's first-run auto-fit means a bare `/transactions` or `/dashboard` lands on the imported data's latest month — the epic's "import your data and *see* your money" payoff needs zero extra work here.

**Evidence base:** reference captures `_bmad-output/implementation-artifacts/visual-qa/spike-reference-parity/reference/import--{upload,preview,result,page}--{desktop,mobile}.png` (auth-app log `41-ref-capture-authenticated-log.md`: standalone page = bare input, help text "Accepted formats: .json, .csv"; rich preview lives in onboarding — "Total: 1880 rows", "Import 1880 transactions" button; result "1880 transactions created, 21 categories created, 34 subcategories created"); gap row RP-F2 in `reference-parity-gap-backlog.md`; 5-1 Completion Notes + Review Findings + `deferred-work.md` 5-1 entries.

## Recommended Approach (binding direction)

**Flow — one client-orchestrated page, three phases, server preview as the single validation authority:**

1. **Select** — a styled dropzone (drag-drop + click-to-browse + keyboard-operable), `accept=".json,.csv"`. Client pre-checks run instantly and are limited to what needs no parsing: extension (`.json`/`.csv`), non-empty file, `file.size <= TRANSACTION_IMPORT_MAX_FILE_SIZE_BYTES` — **read from `@supertool/shared/constants/transaction-import`, never duplicated** (memory `shared-constants-no-duplication`; 5-1 completion note #5). A selected file renders as a card (name, formatted size, replace/clear affordance) — the "clear pre-upload state, not a bare native input" the epic demands.
2. **Preview** — a "Preview" button calls the `previewTransactionImport` server action (FormData → generated client `transactionsImportPreview`, cookie-forwarded via `createServerApiClient`). Success renders the preview panel: `totalRows` / `newRows` / `duplicateRows`, `topLevelCategoriesToCreateList` + `childCategoriesToCreateList`, and near-duplicate warnings from `nearDuplicateClusterList`. A 400 renders a localized validation summary plus the row-aware `details.rowErrorList` strings (see D-E). Pending state disables the controls.
3. **Execute** — an "Import N transactions"-style confirm button re-sends the **same held `File`** to the `executeTransactionImport` server action (generated client `transactionsImport`, 201). The action calls `revalidatePath` for the transactions, dashboard, and categories routes, then returns the report; the page renders an on-page result panel (`inserted`, `skippedDuplicates`, `topLevelCategoriesCreated`, `childCategoriesCreated`, near-duplicate warnings) with links to the transactions list and dashboard (D-H). A double-click on execute is harmless — byte-identical re-runs are idempotent by `import_key` (5-1 AC 3) — but the pending state disables the button anyway.

**No client-side row parsing (D-A — the story's one deliberate divergence, operator-confirm at review):** no papaparse, no client zod row schema, no raw-row preview table. Rationale in the decisions table. Consequence: the page shows the server's semantic preview (counts/categories/duplicates), not the reference's raw-row table.

**⚠️ Framework gate that would silently break the contract:** Next.js caps server-action request bodies at **1 MB by default** — `apps/money-tracker/next.config.ts` sets no `serverActions.bodySizeLimit`, so any 1 MB–5 MiB file would pass the client pre-check and then die at the framework boundary with a generic Next error, and the 413 branch below would never fire. Raise the limit in `next.config.ts` (`serverActions.bodySizeLimit: '6mb'` — above the 5 MiB file limit plus multipart overhead; the option lives under `experimental` in current Next — verify against the installed 16.x) and prove the full-size path live with a 1–5 MiB fixture during QA. The reference's config also lacks this (same latent bug — do not carry its absence as a pattern).

**State & components:** the page RSC (`page.tsx`) does the standard `fetchProfile()` auth gate + `setRequestLocale`, then renders one client orchestrator component that owns `{ file, phase: select|preview|result, actionState }` via a co-located hook. Server data never lands in client state beyond the returned report objects (rule: client state is UI state; the report is the action's return value, rendered directly). Mutations use `useTransition`/`useActionState` pending flags per D9.

**Error mapping (never raw API text as the headline):** the actions return route-local discriminated unions (D-C). Error codes map to localized messages via the `translateError.has(code) ? translateError(code) : translateError(UNKNOWN_ERROR_CODE)` pattern (`TransactionForm.tsx` precedent). **Oversize is mapped by HTTP status, not body code**: a >5 MiB upload that slips past the client pre-check returns **413 with body `code: INTERNAL_ERROR`** (5-1 documented contract, review decision #1) — the action must branch on `response.status === HTTP_STATUS_CODE.PayloadTooLarge` (constant added by 5-1 for exactly this) and return a dedicated `fileTooLarge` error key; never switch on the 413 body's `code`.

**UX copy caveats to honor (5-1 carry-ins, closes two deferred-work "surface in 5.2 UI" items — D-F):**
- Preview's category lists are a **name-only approximation** of execute's `[userId, name, type, parentId]` conflict target — phrase them as "Categories to create" without promising exact counts; the result panel shows the actual created counts.
- Dedup is **positional** (`import_key` = SHA-256 of record + row index): byte-identical re-uploads dedup perfectly; an edited/reordered re-export re-imports the shifted tail. Surface a short info hint on the preview step (duplicate detection applies to unmodified re-uploads).
- Amounts with more than two decimals are rounded half-up on import — fold into the same info hint.

## Acceptance Criteria

1. **First-class upload state (RP-F2 — exceed the reference's bare input, spike §5).** Given the import page at `/transactions/import`, when I select a file via click-to-browse, keyboard, or drag-drop, then I see a styled dropzone (visible drag-over state) and, once selected, a file card (name + human-readable size + replace/clear); client pre-checks — extension `.json`/`.csv`, non-empty, size ≤ `TRANSACTION_IMPORT_MAX_FILE_SIZE_BYTES` — reject bad files instantly with localized messages, reading the shared constants (never re-declared). Full row parsing/validation is deliberately NOT client-side (divergence D-A — operator-confirm at review).
2. **Preview via the 5.1 endpoint (NFR6 — generated client only).** Given a selected file, when I trigger Preview, then a `'use server'` action calls `TransactionsApiService.transactionsImportPreview` (multipart `{ file }`, cookie-forwarded client factory — a hand-written `fetch` is a defect) and the page renders `totalRows`/`newRows`/`duplicateRows`, the top-level and child categories to create, and near-duplicate warnings, with the pending state disabling controls; a validation failure (400 `VALIDATION_ERROR`) renders a localized summary plus the row-aware `details.rowErrorList` entries, and I can replace the file and retry. Preview copy respects the name-only approximation and positional-dedup caveats (D-F).
3. **Confirmed execute with refresh (D9/NFR5).** Given a successful preview, when I confirm execute, then the server action calls `transactionsImport` with the same held `File`, the pending state disables the control, `revalidatePath` refreshes the transactions, dashboard, and categories views, and on success I see an on-page result summary (`inserted`, `skippedDuplicates`, categories created counts, near-duplicate warnings) with working links to the now-populated transactions list and dashboard (4.3 auto-fit lands them on the imported data's latest month).
4. **Errors localized by code/status — never raw API text as the message.** Given any import error, then the headline message resolves from i18n by error code with the `UNKNOWN` fallback (`ActionState` pattern); an oversize upload is mapped by **HTTP status 413** (`HTTP_STATUS_CODE.PayloadTooLarge`) — never by the 413 body's `code` (it stays `INTERNAL_ERROR` per the 5-1 contract) — to the same localized message as the client-side size pre-check; `rowErrorList` diagnostic strings render verbatim under a localized heading (D-E); every error state allows correcting the file and retrying.
5. **Sidebar Import placeholder flips live (epic-4 retro action #3 — part of this story's AC, not a follow-up).** Given the sidebar/drawer navigation, then the Transactions → Import child item (`AppShellSection.tsx` `NAV_ITEM_LIST`) is no longer `disabled`, links to `ROUTES.transactionsImport`, and shows the active state on the import page; `transactionsByCategory` and `transactionsRecurring` stay disabled.
6. **Mobile-usable end-to-end (NFR8 — epic per-story mobile-QA check).** Given a 390px viewport, when I run the whole select→preview→execute flow (touch file selection included — drag-drop is an enhancement, not the only path), then every control is reachable and legible with no horizontal overflow (`documentElement.scrollWidth === innerWidth`).
7. **i18n parity (FR19/FR20).** Given every user-facing string on the page, then a new `transactionsImportPage` namespace is registered in `I18N_NAMESPACE` (`packages/shared/src/constants/i18n-namespace.ts`) and mapped in `localization-messages-file-name-by-namespace.ts`, and `apps/money-tracker/messages/{en,uk}/transactions-import-page.json` land in the same commit — real Ukrainian, ICU interpolation only, `pnpm i18n:parity` green.
8. **Tests (NFR1).** Given the feature, component tests cover the dropzone (idle/drag-over/selected/pre-check-error states), preview panel, result panel, and error mapping (code→message, 413→`fileTooLarge`, `rowErrorList` rendering, `UNKNOWN` fallback); server-action tests (mocked generated client, `create-transaction.test.ts` shape) cover pre-check rejection, preview success/400 pass-through, execute success + `revalidatePath` calls, and 413 status mapping; pre-check util tests cover the boundary (exactly 5 MiB passes, one byte over fails; uppercase `.JSON`/`.CSV` extensions accepted — the server lowercases via `extname(...).toLowerCase()`, the client check must match). The server-action body-size limit is raised in `next.config.ts` so the full 5 MiB contract is reachable (see Recommended Approach), and the 1–5 MiB path is proven live. All repo gates green (`--force` where turbo may replay stale logs).
9. **Visual QA evidence — committed (epic-4 retro D1 standing pattern, Story 1.9 protocol).** Given the rendered page, then `_bmad-output/implementation-artifacts/visual-qa/5-2-import-page/` contains screenshots in **light + dark × 390px + desktop** covering the interactive states — dropzone idle, drag-over/file-selected, preview with data (counts + categories + duplicate rows), row-error state, result panel — compared against the reference captures `import--{upload,preview,result,page}` (both viewports), with observations recorded in the Dev Agent Record. ### Current state of the system this story builds on (preserve, don't break)

- **Generated SDK (5-1, NFR6):** `TransactionsApiService.transactionsImportPreview` (POST `/api/v1/transactions/import/preview`, 200 → `TransactionImportPreviewResponseDto { totalRows, newRows, duplicateRows, topLevelCategoriesToCreateList, childCategoriesToCreateList, nearDuplicateClusterList }`) and `transactionsImport` (POST `/api/v1/transactions/import`, 201 → `TransactionImportResponseDto { inserted, skippedDuplicates, topLevelCategoriesCreated, childCategoriesCreated, nearDuplicateClusterList }`); both take `body: { file: Blob | File }` (multipart, `formDataBodySerializer`); errors typed 400/401/413 as `ErrorResponseDto { statusCode, code, message, details? }`. `NearDuplicateClusterDto { normalizedKey, rawNameList, hasMixedScript }`.
- **Error semantics (5-1):** 400 `VALIDATION_ERROR` with `details.rowErrorList: string[]` — 1-based `"Row N: …"`, collect-all, capped at 50; file-level failures (empty, non-array JSON, missing CSV headers, row cap 3000, unsupported extension) use the same envelope, `rowErrorList` may be absent; 413 body `code` is `INTERNAL_ERROR` (map by status, D-D); 201 is returned even when `inserted: 0` (all-duplicates re-run). BOM'd files and impossible calendar dates are handled server-side (5-1 review patches) — no client compensation needed.
- **Idempotency semantics for UX:** re-executing the identical file is safe (`skippedDuplicates` = all); the operator account already holds the 1880 seeded rows keyed by the same `import_key` derivation, so re-uploading the seed JSON previews as `duplicateRows: 1880` — the AC-9 idempotency-visible capture. Preview never writes (5-1 AC 2).

The row cap needs no client check (server 400 covers it; counting rows client-side would require parsing — D-A).
