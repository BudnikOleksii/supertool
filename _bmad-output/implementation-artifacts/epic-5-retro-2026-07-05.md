## What Went Well

- **Contract-first endpoint/consumer split was the epic's structural backbone — and it worked every time.** 5.1 (import endpoint) shipped the contract for 5.2 (import page); 5.4 (analytics endpoints) shipped the contract for 5.5 (widgets); 5.6 combined a thin new endpoint with its own frontend. In each case the consumer story consumed the just-merged generated client with no re-opening of the backend contract. This mirrors the Epic 2/3 rhythm and kept each PR small and single-concern.
- **Reuse-first held under real temptation, and the epic-4 retro's "wire the placeholders in their owning stories" action landed exactly as planned.** The 2.1 seed ingest engine became the import write path verbatim (5-1 D-C — `runImport` wraps `seedTransactions` in one `db.transaction`, keeping D7 literally true); the `/breakdown` + `/trend` recursive-CTE / `generate_series` patterns became top-categories, daily-spending, and by-category (5-4, 5-6) with no new algorithm; `transactionsFindAll`'s already-subtree-aware `categoryId` (Story 2.5) powered the by-category detail with **zero new list endpoint** (5-6 D-1); and the 5-2 import components — built props-in/callbacks-out *specifically* so 5.3 could lift them — were `git mv`'d into app-wide homes and reused in onboarding with no behaviour change (5-3 Task 4). Both disabled sidebar placeholders flipped live in their owning stories (Import → 5-2 AC5, By-category → 5-6 Task 9).
- **The money-as-strings discipline (D1) was flawless across the epic's heavy money surface.** Six endpoints' worth of aggregation, all arithmetic in Postgres, `decimal.js` only at the ingest boundary, counts fenced as numbers at the render edge. The marquee correctness property — `totalExpense` (window `SUM(SUM()) OVER ()` computed pre-LIMIT) reconciling *exactly* with the summary's `expense`, and by-category expense totals reconciling exactly with `breakdown` — was asserted decimal-safe in Testcontainers for 5-4 and 5-6 (FR18). No float ever touched money.
- **A discovered cross-user defect was fixed forward, inside the epic, before it could bite.** 5-1 found that the global `transactions_import_key_unique` index would make a second user's import of a file the first user already imported silently insert zero rows — the exact path 5.3 onboarding would hit. It was fixed *then* (composite `(user_id, import_key)` index, migration `0004`, two-user Testcontainers coverage), so 5.3 could treat cross-user scoping as settled and "do not re-plan" (5-3 context). Risk was retired at its source, not deferred.
- **The committed-visual-QA standing pattern (epic-4 D1) held for four consecutive UI stories, and backend-only stories handled the gate honestly.** 5-2/5-3/5-5/5-6 each committed a light+dark × mobile+desktop matrix with an evidence table and reference-comparison notes; 5-5 caught a real 390px overflow defect in QA (recharts' hidden tooltip wrapper rendering off-canvas at `right:1070`) and fixed it with an `overflow: hidden` clip, re-verifying `scrollWidth === innerWidth`. 5-1 and 5-4, being backend-only, *stated* visual-QA N/A in the Dev Agent Record so the reviewer would not flag a missing gate — the discipline is now nuanced, not cargo-culted.
- **The autonomous on-branch adversarial review + fix cycle caught real must-fix defects before PR.** 5-1's review caught two: impossible-but-in-range calendar dates (`02/30/2025`) passing validation then 500-ing inside the DB transaction, and UTF-8 BOM files rejected with misleading errors — both fixed (calendar round-trip via the just-lifted `checkIsCalendarDate`; `bom: true` + `LEADING_BOM_PATTERN`) and re-reviewed to APPROVE. 5-2 caught an unhandled server-action rejection bypassing the error path and a load-flaky test — both fixed. 5-3/5-4/5-5/5-6 landed with **zero must-fix** findings, a visible maturity trend across the epic.
- **The epic-4 divergence-sign-off guardrail was adopted wholesale and produced a clean paper trail.** Every deliberate departure from the reference carried an explicit `D-x` decision with rationale and an "operator-confirm at review" flag — preview-as-separate-endpoint (5-1 D-A), no onboarding module (5-3 D-B), constant catalog vs DB table (5-3 D-C), plain-shell chrome vs route group (5-3 D-F), no client-side parsing (5-2 D-A), range-vs-year/month daily-spending (5-4 D-1), analytics-module placement for by-category (5-6 D-3), accordion-on-landing (5-6 D-5). Nothing diverged silently.

## Challenges & Recurring Patterns

1. **The "operator-confirm at review" flags never got a live operator in an unattended pipeline.** The epic-4 retro's divergence-sign-off guardrail assumed a human would confirm each flagged divergence *at spec review or code review*. In practice every 5-x story ran autonomously and the flags rode all the way to the PR description, where the human confirmation is implicit in the merge rather than an explicit recorded decision. The guardrail still worked (it forced every divergence to be named and justified up front, and none were rejected), but the "sign-off" is really "merge-time acceptance," and several genuinely product-shaped divergences (e.g. dropping the reference's onboarding module, replacing the month stepper with a filter bar on the dashboard, accordion-on-landing) were adjudicated by the dev agent's judgment, not the operator's. Low harm this epic; worth naming so the confirmation step is deliberate.
2. **The charter's "no schema change" and "papaparse" assumptions were both overridden by better decisions discovered in dev.** Two migrations landed in a nominally schema-stable epic (composite import-key index in 5-1, `onboarding_completed` in 5-3), each bounded, justified, and flagged per D3 — but the charter's planning note was simply wrong about the schema surface. Similarly the charter's 5.2 evidence note prescribed papaparse; 5-2 D-A deliberately dropped it because the 5-1 server preview is a strictly richer, single source of validation truth (a client zod/papaparse pass would duplicate and silently diverge from the server rules — the exact defect class the regex-lift had just eliminated). Both were the right calls, but they show the epic charter's implementation notes are advisory, not binding, and dev-time reality corrected them.
3. **The deferred ledger grew by ~31 items, heavily concentrated in three recurring clusters** (see the catalogued list below). The reviews are thorough and the items are genuinely low-severity, but three themes repeat *within* the epic and *across* prior epics: (a) **shape-only date validation** — `CALENDAR_DATE_PATTERN` checks `^\d{4}-\d{2}-\d{2}$` with no real-calendar validity and no `dateFrom <= dateTo` guard, first deferred in Epic 2 (2-2), again in Epic 3 (3-1), fixed *only* at the 5-1 import boundary, and surfacing yet again in 5-5's dashboard filter parser; (b) **analytics range robustness** — no upper bound on a selected span (5-5) and no deterministic tie-break secondary sort (5-4), both inherited from the breakdown/trend endpoints; (c) **dashboard filter UX** — clearing one date input resets both bounds, an over-keyed trend Suspense boundary, and a missing `NO_CURRENCY` guard on recent-transactions (all 5-5). These are cheap individually and never fired in the seeded happy path, but the date-validation one is now ~3 epics old.
4. **Backend surface returning after a frontend-only epic re-imported the shared-environment friction.** 5-1 hit the same class of local-infra pain the prior backend epics did: a Testcontainers hang (Docker Desktop's containerd image store misses the image-exists check → a pull invokes `docker-credential-desktop`, which blocks on keychain in a non-interactive shell — worked around with a scratch `DOCKER_CONFIG`), plus a transient undici socket-parse flake under full-parallel test load. Neither was a code defect and both were diagnosed, but they cost debugging time and are latent for every future backend story. TS 6.0 also stopped auto-including `@types`, forcing a `"types": ["multer"]` workaround that itself became a deferred item (it disables other `@types` globals; revisit as `["multer","node"]`).
5. **Mixed model use across the epic.** 5-1 ran on Fable 5; 5-3/5-4/5-5/5-6 on Opus 4.8 (1M). Not a problem — all shipped clean — but noted for reproducibility since the earliest, most novel-ground story (the import engine) used a different model than the rest.

## Key Insights

1. **Contract-first splitting is now a proven default for any endpoint-plus-UI feature, not just a scheduling convenience.** Landing the endpoint (with its full Testcontainers suite and committed generated client) one story ahead of its consumer meant the UI story never blocked on backend uncertainty and never re-opened the contract. It also made the "backend-only story declares visual-QA N/A" and "frontend-only story declares drift-gate no-op" boundaries crisp. Keep splitting Epic 6's endpoint work (6.5 caching) from its consumers the same way.
2. **Divergence flags need a real resolution owner in an unattended pipeline.** The guardrail successfully forces every divergence to be named — but "operator-confirm at review" is a no-op when no operator is in the loop. Either the flags should be triaged by the operator in a batch before merge (a lightweight PR-time checklist), or the convention should be renamed to "recorded divergence, dev-adjudicated, operator may overrule on PR" so the accountability is honest. The divergences this epic were all sound; the *process* should not pretend a confirmation happened that didn't.
3. **A recurring low-severity deferral eventually earns a dedicated fix — the date-validation debt is there now.** Shape-only date validation has been deferred in Epics 2, 3, and again in 5-5, and 5-1 proved the fix is cheap (round-trip the parsed ISO through the shared `checkIsCalendarDate`; add a `dateFrom <= dateTo` guard). Epic 6 adds search (6.4), a fresh date-range surface — the natural, no-longer-optional trigger to lift a shared calendar-date + range-order validator across *all* analytics/transactions date DTOs at once, exactly as the epic-3 deferral note prescribed ("if hardened, do it repo-wide").
4. **The charter's implementation notes are a starting hypothesis, not a spec.** Two charter assumptions (no schema change; papaparse) were correctly overridden in dev. This is healthy — the dev agent had better information at implementation time — but it argues for treating epic-level "reuse X / no change to Y" notes as *defaults to challenge*, with the challenge recorded as a `D-x`, rather than as constraints. The stories already do this well; the insight is to keep expecting it.
5. **Reuse compounds when components are designed for it one story early.** The single highest-leverage decision of the epic was 5-2 building its import components props-in/callbacks-out "so a lift to `src/components/` stays mechanical if 5.3 needs it." When 5.3 arrived, the lift was a `git mv` + import-path update with every moved test green. Designing for the *next* story's reuse — not just the current one's — paid off directly.
