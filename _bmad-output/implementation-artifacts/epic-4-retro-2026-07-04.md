## Challenges & Recurring Patterns

1. **Two of four stories had their own binding spec sections overturned mid-story.** 4.1 shipped a header-nav + flat drawer, then pivoted to the reference-style persistent collapsible sidebar (interim `AppNav` built, tested, QA'd — then deleted). 4.2's spec declared a *binding* Architecture Decision to preserve the desktop table via a CSS display-toggle; the operator rejected the table on first review and directed grouped cards at all widths + pulling the cascading picker forward. Root cause (synthesized from both records): **story creation optimized for "no desktop regression" while the epic's stated bar was "reference parity"** — the specs were more conservative than the product direction, and the conservatism was only surfaced by rendered UI, not by spec review. The rework cost was real (a full component built twice in 4-1; a dual layout built then halved in 4-2).
2. **ED1 is under tension with the parity strategy — first formal waiver recorded.** The 4.2 `CategoryPicker` is a close structural reproduction of the reference component, reviewed against ED1 ("patterns may be carried, code may not") and **accepted as a sanctioned per-component waiver** because the project's explicit strategy is reference parity. Reasonable — but the rule and the strategy now visibly pull apart, and waiver-by-waiver adjudication in review is where that tension will keep landing.
3. **The shared mutable dev environment became the epic's recurring time sink.** Two incidents: a stale `next-server` from another `.claude/worktrees/*` checkout occupying :3000 and serving old code during 4-2's QA, and stray QA-created transactions (2026-06-15 rows) making 4.3's auto-fit look broken until the DB was truncated and re-seeded (the idempotent seed cannot remove API-created rows). Both were diagnosed correctly, both became memories (`worktree-dev-server-stale-qa`, `seed-idempotent-truncate-before-reseed`) — but both were paid for in debugging time. Parallel-worktree delivery multiplies exposure to the single :3000 + single database.
4. **The deferred ledger keeps growing append-only** (8 new items this epic; consolidation was explicitly de-prioritized for the PoC in the epic-3 retro — standing decision, not re-litigated here). The epic-2-era regex-duplication item is now three epics old (see follow-through #2).

## Key Insights

1. **Committed evidence as a per-story AC beat both alternatives.** Epic 1–3 cycled through hand-run-and-discard (eroded) and automate-it (never happened, then consciously dropped). Epic 4's third way — evidence is an acceptance criterion, committed to the repo, reviewed as part of the story — held for four consecutive stories with zero erosion and one real defect caught. This is now the project's proven QA pattern for UI work; keep it in every Epic 5–7 story (already mandated by the epics.md evidence-reference convention).
2. **When the product direction is "match the reference," story specs must default to the reference — divergences need operator sign-off at spec time, not at first-render review.** Both course corrections were the same failure: the spec chose to preserve current supertool UI where the reference did something else, and the operator overruled it once rendered. The cheap fix is at story creation: any deliberate divergence from the reference gets an explicit, operator-confirmed callout in the story before dev starts.
3. **Parallel-worktree delivery needs environment hygiene as a first-class step.** Verify which checkout serves :3000 and what state the DB is in *before* trusting any live QA — both epic-4 incidents were pre-flight-checkable. The memories exist; treat them as a mandatory pre-QA checklist, not tribal knowledge.
4. **A quality-only epic can ship outsized value fast.** Four stories, ~two days wall-clock, no new backend surface — and the product went from "broken on a phone" to exceeding the reference on every touched screen. The discipline (evidence ACs, adversarial review, hard rules) did not slow that down; it is what made the course corrections safe.
