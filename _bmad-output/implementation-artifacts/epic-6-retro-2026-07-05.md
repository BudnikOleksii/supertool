The three-epic-old date-validation debt is finally, verifiably gone.
- **The contract-first / additive-contract discipline produced near-zero generated-client drift on three consecutive stories.** 6-3's DTO refactor (extracting `TransactionFilterQueryDto`, composing `FindTransactionsQueryDto` via `IntersectionType` in an *order-preserving* argument order) kept `transactionsFindAll` byte-identical while adding only the export op; 6-4 added `search` to the `FindTransactionsQueryDto` **body only** so the export contract stayed byte-identical and the client diff was a *single additive line* (`search?: string`); 6-5 changed the contract not at all (drift gate a literal no-op). Each story explicitly verified the drift was additive-only with `git status --porcelain packages/shared/src/generated`. The "extend existing endpoints additively, keep the shipped contract byte-identical" rule was treated as a hard constraint, not an aspiration.
- **The two-surface (by-date list + by-category detail) UI reuse pattern was established once in 6-2 and reused verbatim in 6-3.** 6-2 built the bulk-delete selection primitives (provider/context/checkbox/action-bar/dialog) as shared components wired on both surfaces — "reuse the shared primitives, do not fork them" (D-6). 6-3 then built one route-agnostic `ExportMenu` (props in / callbacks out) and wired it into both page headers. The reference itself only wires bulk-delete on by-category; supertool exceeded it on consistency *and* touch-usability, and the pattern is now a standing convention for any transactions-surface feature.
- **Every security-sensitive surface this epic added was verified with a dedicated integration test, not just asserted.** Three genuinely dangerous surfaces landed — bulk-delete (destructive, cross-user risk), search (SQL/LIKE injection risk), and the cache (cross-user leakage risk) — and each carries proof: 6-2's `deleteManyScoped` uses `and(eq(userId), inArray(id))` with a Testcontainers test proving user A cannot delete user B's rows (they land in `failedList`, none deleted); 6-4's `ilike(note, bound-param)` with LIKE-metachar escaping has integration tests proving `%`/`_` match literally and a `'; DROP TABLE transactions;--` payload is inert (the table survives); 6-5's cross-user cache isolation is proven end-to-end via HTTP with two signed-in users. The "a cross-user leak is a security defect and MUST be covered by an integration test" standard was enforced.
- **The in-house-over-dependency ethos held under three separate temptations, each with a plausible off-the-shelf alternative.** Hand-rolled CSV (6-3) bought explicit OWASP formula-injection neutralization that `csv-stringify` does not do by default; the local debounce hook (6-4) avoided a lodash/`use-debounce` dep for ~10 lines of `useEffect`+`setTimeout`; the in-house cache (6-5) got O(1) per-user bulk invalidation that a flat `cache-manager` KV store cannot do without tracking key-sets anyway. In each case the in-house choice was not just "no dep" — it was *better fit* for a hard rule or a real requirement, and each was exhaustively unit-tested.

## Challenges & Recurring Patterns

1. **A dev subagent crashed mid-QA on 6-1 (ECONNRESET) — the orchestrator recovered, but one AC-8 capture was left incomplete.** The initial 6-1 dev subagent finished implementation and most of the visual-QA matrix, then died on an infrastructure error before committing. The orchestrator recovered correctly — re-ran the full gate suite green (`TURBO_FORCE=true`), finalized the Dev Agent Record, and committed with no code change during finalization. This is a genuine resilience win (the pipeline did not lose the work). But the crash landed *during* the category-picker-open capture, so that one light/dark × 390/desktop matrix was never completed and a malformed partial file was removed. The reviewer judged it acceptable (the picker is unchanged 4-2 code, regression-guarded by the updated `TransactionForm.test.tsx`, not in the 6-1 diff), but the AC-8 picker evidence is a standing small gap. Lesson: mid-run subagent crashes are survivable via gate-verify-then-finalize, but a crash during QA can silently drop an evidence artifact — the recovery path should explicitly re-check the visual-QA matrix for completeness, not just the gates.
2. **The flaky CI Testcontainers `57P01`/`ProcessInterrupts` teardown race hit 6-1's PR and was papered over by a re-run.** 6-1's PR CI failed on a Postgres teardown race — the container was stopped while the pg pool still had live connections, surfacing `57P01` / `ProcessInterrupts` from the integration suite's `afterAll`. It was resolved by simply re-running CI (it passed on retry), which is a workaround, not a fix. This is latent for every backend story's CI and will recur. The real fix is to **drain/close the pg pool before stopping the container** in the integration teardown — a small, one-time change to the shared `postgres-container.ts`/`afterAll` helper. Carried as an action item so the next backend epic doesn't keep paying the re-run tax.
3. **6-2 concentrated the epic's deferred ledger — 8 of ~18 items — mostly in bulk-delete selection edge cases that are unreachable at the current page size.** The review was thorough and correct, but several 6-2 nice-to-haves describe *dead paths at PoC scale*: the over-cap select-all notice is unreachable because page size is 50 and selection resets per page (a user can never accumulate >50 of the 100 cap); the not-found re-selection re-selects ids whose rows are already gone after `revalidatePath` (the only reason code is permanent `NOT_FOUND`, so "retry" deletes nothing and the action bar shows "N selected" for rows with no checkbox); Escape during an in-flight delete can drop total-failure feedback. None fire in the seeded happy path, but they reveal a small design mismatch: the selection model was adapted from the reference's *transient-failure* assumption, while supertool's backend only ever returns *permanent* not-found. Worth a small design note when bulk-delete is next touched, so the re-selection semantics match the actual failure taxonomy.
4. **6-3 and 6-3-review surfaced a cluster of CSV/export hardening latents that are correctly deferred but share a root.** The CSV injection guard is applied to *all* columns including `Amount` (a leading-`-` amount would become `'-…`) — latent only because the DB `amount > 0` check and positive-amount validators make a negative amount non-triggerable; the leading-whitespace formula bypass (` =CMD`) is not neutralized (AC-3 specifies first-char only); `downloadBlob` revokes the object URL synchronously right after `click()` (rare Firefox large-download cancellation); `parseSeedDate` accepts impossible calendar days (`2025-02-30`) — a pre-existing weakness the ISO widening inherited, caught by Postgres at insert. All five are genuinely low-severity, but they cluster around "the export/round-trip path trusts its inputs more than the rest of the codebase does" — a theme to watch if export ever accepts user-authored files rather than DB rows.
5. **The two PoC-acceptable cache limits (6-5) are deliberate deferrals, but they are real and should not be forgotten.** 6-5's review APPROVEd with two recorded deferrals: a cache-aside **TOCTOU race** (two concurrent misses can both compute and both set — harmless with `structuredClone` and identical computations, but a thundering-herd inefficiency) and **no hard cache size cap** (the two-level `Map` grows unbounded in userId × distinct-query space, bounded in practice only by the 5-min TTL and single-operator usage). Both are correct calls for a single-instance local PoC, but both become real the moment supertool runs multi-user or multi-instance — exactly the transition that would also force the RP-D7 Redis decision to be revisited. They are coupled: the day Redis arrives, both of these evaporate.
6. **The charter's "search if warranted" (P2) and "or repeated scoped deletes" hedges were both resolved firmly in dev, in the exceed-the-reference direction.** The charter left 6.4 search as optional ("P2 — include if the list UX warrants it") and offered bulk-delete as either a batch endpoint *or* fanned-out single deletes. Dev resolved both decisively: search shipped as a full additive-param feature with a trigram index (and became the carrier for the date-validation debt), and bulk-delete got a real single-batch endpoint (D-1: fanning out N deletes can't return a batch count, isn't one scoped op, multiplies round-trips). Both were the right calls, and — consistent with the Epic 5 insight — confirm that charter implementation notes are hypotheses to resolve in dev, not constraints.

## Key Insights

1. **Naming a *specific owning story* for each deferred item at the previous retro is what turned a wish-list into a 6-for-6 close-out.** Epic 5's retro didn't just list debt — it assigned each item to the Epic 6 story whose natural surface would trigger it (date-validation → 6-4 because it adds a date surface; range-robustness → 6-5 because cache keys need bounded ranges; bulk-delete-on-by-category → 6-2; export-button → 6-3). Every one landed. The lesson is procedural: deferred items with a named trigger get done; deferred items without one accrete. Epic 6's own deferrals below are assigned the same way.
2. **"Additive-only contract" is now a demonstrated discipline, not just a goal — and it needs the same verification ritual every time.** Three stories in a row kept the shipped contract byte-identical while extending it, each proven with `git status --porcelain packages/shared/src/generated` and (6-3) an explicit "verify `transactionsFindAll` unchanged" step baked into the task. The `IntersectionType` argument-order trap (order churns the generated query-param order) is a real, subtle hazard that 6-3 navigated correctly and 6-4 respected. Keep the drift-verification step explicit in every contract-touching story; the byte-identical guarantee is cheap to state and expensive to lose silently.
3. **When adapting a reference pattern, adapt its *assumptions* too — 6-2's selection model inherited a transient-failure assumption supertool's backend never produces.** The reference's bulk-delete re-selects failed ids "for retry," which makes sense when failures are transient. supertool's backend only returns permanent `NOT_FOUND` (the row is gone after revalidation), so the re-selection re-selects rows that no longer render and a "retry" deletes nothing. The pattern was copied faithfully but its precondition wasn't. Lesson: when lifting a reference behavior, check that the *why* still holds against supertool's actual data model, not just the *what*.
4. **The autonomous pipeline is resilient to subagent crashes but not yet to crash-dropped artifacts.** 6-1 proved the orchestrator can recover a crashed dev subagent by verifying gates and finalizing — the work survived. But the crash silently dropped a visual-QA capture, and the gate-verify path didn't catch it because screenshots aren't a gate. Recovery-after-crash should include an evidence-completeness check (does the visual-QA matrix match what the ACs require?), not only a gate re-run.
5. **A flaky test that's "fixed" by a re-run is unpaid debt that compounds per backend story.** The `57P01` teardown race passed on retry, which is tempting to leave alone. But every future backend story's CI carries the same dice-roll, and re-runs cost wall-clock and erode trust in a red build. The one-time pool-drain fix retires the flake permanently; deferring it keeps paying it. This is the backend analogue of Epic 5's date-validation lesson — a recurring low-severity annoyance eventually earns a dedicated fix.
