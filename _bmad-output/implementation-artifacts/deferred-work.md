## Deferred from: code review of 5-1-transaction-import-endpoint (2026-07-04)

- Import dedup is positional: `buildImportKey` mixes `rowIndex` into the SHA-256 (architecture D2 mandates record + row index), so inserting/removing/reordering one row in an already-imported export gives every subsequent row a new key — preview under-reports `duplicateRows` and execute re-inserts the whole shifted tail. Byte-identical re-runs are idempotent (integration-tested); edited re-exports are not. Either accept and surface in the 5.2 UI copy, or move to a content-only key (which needs a within-file duplicate-row decision, since identical rows currently coexist via `rowIndex`). [apps/api/src/database/seeds/build-import-key.ts, apps/api/src/modules/transactions/transactions-import.service.ts]

The near-duplicate report is the surfacing mechanism today; story 5-1 explicitly forbade redesigning the keying. Resolve child ids by (parent, name) and key hierarchy by (name, type) when the engine is next opened. [apps/api/src/database/seeds/seed-transactions.ts, apps/api/src/database/seeds/derive-category-hierarchy.ts]

- Import row-error list is capped at `IMPORT_MAX_REPORTED_ROW_ERRORS = 50` with no total-error count or truncation marker in `details.rowErrorList` — a very dirty large file forces blind iterate-fix-reupload cycles. ## Deferred from: code review of 2-4-edit-delete-transactions (2026-06-15)

- **fetch-transaction swallows non-404 errors into a phantom "not found" redirect** — `fetch-transaction.ts` destructures only `{ data }` and returns `data ?? null`; the edit page redirects any null to `/transactions`. A 401 (expired session) or 500 is therefore indistinguishable from a genuinely missing transaction and silently bounces the user to the list instead of sign-in/an error. Matches the established `fetch-*` read-action template (codebase-wide), and `fetchProfile` auth-guards earlier so the window is narrow; address as a cross-package read-action convention if desired. [apps/money-tracker/src/actions/fetch-transaction.ts]
- **updateScoped non-atomic UPDATE-then-SELECT (TOCTOU)** — `updateScoped` runs `UPDATE ... RETURNING { id }` then a separate `findOneByUserIdAndId` reload outside a transaction; a concurrent DELETE in the window makes the reload return null and the service throws a misleading 404 after a successful write. Same class as the already-tracked create TOCTOU and explicitly acknowledged in the story Dev Notes as acceptable under the single-operator local runtime (`onDelete: restrict`, narrow window). A wrapping transaction would close it. [apps/api/src/modules/transactions/transactions.repository.ts]
- **Edit-mode page-jump redirect off-by-one on same-date clusters** — `getTransactionPage` counts rows with `date > editedDate` (`getNextCalendarDate`) then `floor(count / pageSize) + 1`; list ordering is `desc(date), desc(id)`, so for an edited row that shares its date with others the page math ignores the same-date `id` tiebreaker and can land the user on a page that does not contain the just-edited row. Inherited verbatim from the create flow's known approximation; reused for edit. [apps/money-tracker/src/app/[locale]/transactions/utils/redirect-to-transaction-month.ts]

## Deferred from: code review of 4-3-first-run-period-auto-fit (2026-06-17)

- `getPeriodFromDate` silently coerces a malformed/short/empty API `date` to the current month (it routes through `parsePeriod`'s silent current-month fallback), and that branch is untested. Harmless given the API `date`-column contract (always `YYYY-MM-DD`), but the silent substitution would mask a data-integrity problem. - The latest-transaction lookup is implicitly coupled to `DEFAULT_SORT_BY` (=`date`) and `DEFAULT_SORT_ORDER` (=`desc`) remaining date-descending. The story spec explicitly mandated reusing those shared constants (no magic strings), so this is spec-directed. Decouple via a dedicated `LATEST_SORT_BY`/`LATEST_SORT_ORDER` constant if the default list sort ever changes. [apps/money-tracker/src/actions/fetch-latest-transaction-date.ts:16-24]
- `getCurrentPeriod()` reads server-local timezone (`new Date().getFullYear()`/`.getMonth()`) while transaction dates are timezone-free `YYYY-MM-DD` strings, so the auto-fit/min-clamp boundary that compares against `getCurrentPeriod()` is environment-sensitive near a month edge — the same data could resolve to a different default landing month depending on where the server runs. Pre-existing (`getCurrentPeriod` unchanged by this story). Revisit if multi-timezone deployment is introduced. [apps/money-tracker/src/utils/period.ts:32-36]
